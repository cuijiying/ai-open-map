# 数据库设计

库名 `ai_open_map`，编码 UTF-8。几何一律是 WGS84，`EPSG:4326`。扩展有两个：`postgis` 负责几何，`pg_trgm` 负责名称的模糊匹配索引。

脚本在 `sql/schema.sql`。下面按“谁写入”来看表。

## 1. 表怎么分工

| 表 | 写入者 | 读取者 | 作用 |
| --- | --- | --- | --- |
| `ingest_job` | 入库服务 | 入库服务、页面 | 一次下载解析任务 |
| `ingest_job_log` | 入库服务 | 页面 | 阶段日志 |
| `osm_feature_stage` | 入库服务 | 入库服务 | 无索引缓冲，解析过程只写这里 |
| `osm_feature` | 入库服务在发布时整表替换 | 地图服务 | 地图真正读取的要素 |
| `ai_model_config` | 对话服务 | 对话服务 | OpenAI 兼容模型 |

地图服务不写 `osm_feature`。对话服务不写要素表。下载和解析只写缓冲表。几何、索引建在旁路表上，发布时用一次短事务替换该省分区，其他省的切片查询不会被这次写入挡住。

## 2. 任务表

`ingest_job` 的状态只有 `RUNNING`、`SUCCESS`、`FAILED`。`phase` 表示阶段：`DOWNLOAD`、`PARSE`、`IMPORT`、`INDEX`，结束时是 `SUCCESS` 或 `FAILED`。`progress` 是 0 到 100 的整数。`trigger_type` 是 `MANUAL`（页面）或 `SCHEDULE`（每天 03:00）。

同一时刻只能有一条 `RUNNING`。普通唯一约束做不到“只对某个状态唯一”，所以用部分唯一索引：

```sql
CREATE UNIQUE INDEX uq_ingest_job_running
    ON ingest_job (status)
    WHERE status = 'RUNNING';
```

第二个手动任务会在插入时失败，服务把它转成“已有任务在跑”的提示。

`layer_counts` 是 JSONB，发布成功后写入各图层数量，页面不必再扫一遍大表才能显示这次任务的结果。`file_bytes` 记录下载文件大小。这次成功任务的文件是 43,506,356 字节。

`ingest_job_log` 按 `job_id, id` 递增。页面用 `afterId` 续拉，不用每次把全部日志重新取回。

## 3. 要素表

一行是一个被分类器接受的 node 或 way。

| 列 | 含义 |
| --- | --- |
| `osm_id` | OSM 原始 id。node 和 way 的 id 空间不同，所以要和 `osm_type` 一起看 |
| `osm_type` | `node` 或 `way`。没有 `relation` |
| `layer` | 九个图层之一，见下表。检查约束和 Java 的 `Layers.ORDER` 必须一致 |
| `sub_type` | 图层内类型。道路是 `motorway`、`residential`；兴趣点常常是 `amenity=university` 这种 `键=值` |
| `name` | 名称，可空 |
| `props` | 保留的一小部分 OSM 标签，JSONB |
| `geom` | `geometry(Geometry, 4326)`。点、线、面都允许，因为不同图层几何类型不同 |
| `job_id` | 发布这次数据的任务 |

九个图层和几何：

| layer | 中文 | 常见几何 |
| --- | --- | --- |
| landuse | 土地利用 | 面 |
| water | 水体 | 面 |
| building | 建筑 | 面 |
| waterway | 水系线 | 线 |
| railway | 铁路 | 线 |
| highway | 道路 | 线 |
| boundary | 行政区划 | 线 |
| poi | 兴趣点 | 点 |
| place | 地名 | 点 |

`Layers.ORDER` 的顺序也是前端叠放顺序：用地和水体在下，道路和地名在上。

索引：

| 索引 | 类型 | 给谁用 |
| --- | --- | --- |
| `idx_osm_feature_geom` | GIST(`geom`) | 瓦片的 `&&`、视野分析 |
| `idx_osm_feature_layer` | btree(`layer`, `sub_type`) | 按图层统计、按子类过滤 |
| `idx_osm_feature_name` | GIN(`name gin_trgm_ops`) | `ILIKE '%关键词%'` |

三元表达式索引依赖 `pg_trgm`。没有它，`CREATE INDEX ... gin_trgm_ops` 会失败，名称搜索会退化为全表扫描。

## 4. 为什么要缓冲表和分区

`osm_feature` 按 `region_code` 做 LIST 分区，一省一个分区。`osm_feature_stage` 是 `UNLOGGED`。崩溃时缓冲表可以丢，已发布的分区保持上一次的完整数据。列里几何先存 WKT 文本，发布时才 `ST_GeomFromText(wkt, 4326)`。解析循环里不做空间函数，解析和数据库几何计算分开。

发布分两段，地图切片在这两段里都能读：

1. 旁路表 `osm_feature_load` 接收几何，并在这张表上建 GIST、图层和名称索引。这一步不修改正在被切片读取的分区。
2. 短事务里摘掉该省旧分区、挂上旁路表、删掉旧分区。事务结束前，正在进行的切片查询仍看到旧分区；结束后看到新分区。其他省的分区不拿排他锁。

因此下载、解析、建索引期间，已经发布的省份可以继续出矢量切片。同一时刻仍然只有一个入库任务，因为缓冲表只有一张。

已有的普通表会在入库服务启动时改成分区表，原有行按 `region_code` 搬进去。主键是 `(id, region_code)`，因为分区表的主键必须包含分区键。

解析写入用的是 `COPY ... FROM STDIN WITH (FORMAT csv)`，走 PostgreSQL 驱动的 `CopyManager`，不走 MyBatis。Druid 连接池上的连接要 `unwrap` 成 `BaseConnection` 才能拿到这个 API。

## 5. 模型表

`ai_model_config` 保存名称、`base_url`、`api_key`、模型名、温度和 `enabled`。`base_url` 约定以 `/v1` 结尾，例如 `http://127.0.0.1:11434/v1` 或 `https://api.openai.com/v1`。

同时只启用一个模型：启用新的之前会把其他行的 `enabled` 置为 false。没有任何启用模型时，对话只走内置指令。接口返回的密钥是打码后的，库里的列仍是原文。这是本地学习环境的做法，不适合直接暴露到公网。

## 6. 和 SQL 相关的两个坑

写在构建记录里，这里只保留和表结构有关的结论：

- Druid 统计过滤器不要合并 SQL。建扩展、部分索引、GIN、UNLOGGED 都会让合并器报错。
- 可空查询参数不要写成 `#{layer} IS NULL`。PostgreSQL 无法推断未类型化的 NULL。图层条件用 MyBatis 动态 SQL 拼进去。
