# 多省切片学习笔记

这份笔记写给第一次读本仓库的人。它解释 2026-10-21 合进主分支的那一组提交：地图可以同时画出多个省，而且某个省正在下载、解析、建索引时，已经发布的省份切片仍然能打开。

先读完第 1 到第 4 节，建立整体画面。后面的章节按一条数据的真实路径展开，可以对照着代码看。接口清单仍以 [运行与接口](03-运行与接口.md) 为准，表结构仍以 [数据库设计](02-数据库设计.md) 为准。

## 1. 今天之前，系统已经能做什么

系统是一个本地 WebGIS，数据来自 OpenStreetMap 的省级提取文件（PBF）。五个进程的分工见 [架构与技术栈](01-架构与技术栈.md)。和今天有关的只有两条链路：

- 入库服务把 PBF 解析成要素，写入 PostgreSQL / PostGIS 的 `osm_feature`。
- 地图服务按请求从这张表里切出矢量瓦片，浏览器里的 MapLibre 把瓦片画出来。

今天之前，表里已经有 `region_code`（`anhui`、`zhejiang` 这种省级代码），页面也可以切换省份。但地图一次只请求一个省。重新入库某个省时，发布阶段会在 `osm_feature` 上做删除和插入。表越大，这次写入持有的锁越久，别的省的切片查询就越容易被堵住。

## 2. 今天要解决的两件事

用一个具体场景来记：

1. 安徽已经在库里，地图上正在看合肥的道路。
2. 这时开始下载并解析浙江。
3. 下载和解析可能要几分钟。这几分钟里，安徽的瓦片必须还能拖动、放大。
4. 浙江发布完成后，地图上可以同时看到安徽和浙江，不用来回切换。

对应两句实现目标：

- **入库过程中切片仍可用。** 慢的工作不要发生在地图正在读的那张表上。
- **一张地图同时画多个省。** 一次瓦片请求可以带上好几个 `region_code`。

## 3. 先记住这几个词

| 词 | 在本项目里的意思 |
| --- | --- |
| 要素 | 表 `osm_feature` 里的一行。一条路、一条河、一栋房子、一个地名都是一行 |
| 图层 | `highway`、`water` 等九类。浏览器按图层分别要瓦片 |
| 瓦片 / 切片 | 把世界按缩放级别切成小方块。某一块的地址是 `/{图层}/{z}/{x}/{y}.pbf` |
| MVT | Mapbox Vector Tile。瓦片文件的格式，里面是简化后的几何，不是一张图片 |
| PBF | OSM 的压缩数据文件。入库服务下载的就是它 |
| 分区 | PostgreSQL 把一张大表按某列拆成多张物理子表。这里按 `region_code` 拆，一省一张 |
| 事务 | 一组 SQL 要么一起成功，要么一起撤销。别的连接在提交前看不到写了一半的结果 |
| 锁 | 数据库为了不让两个人把同一行改乱而做的等待。排他锁会让读查询也排队 |
| MVCC | PostgreSQL 的读法：正在进行的事务提交前，别的查询仍看到旧版本 |

不需要先把这些词背下来。读到第 7 节和第 8 节时再回来看。

## 4. 今天的提交，以及最后留下了什么

同一天有三条实现，后两条是同一目标的两种写法。它们都已经在主分支的历史上，但最终跑起来的代码是合并时收成的一套。

| 提交 | 它尝试的做法 | 最终是否还在跑 |
| --- | --- | --- |
| `d8eadb6` | 瓦片增加 `regions=anhui,zhejiang`。发布仍是「删掉该省再插入」，只是把 `ANALYZE` 挪到事务外面，缩短锁的时间。页面自动把所有已入库的省都画出来 | 多省参数这个想法留下了。发布方式被后面的分区替换掉了 |
| `74037b7`（分支 `cursor/multi-province-tiles-1971`） | 表改成按省分区。几何和索引先建在一张公共旁路表 `osm_feature_load` 上，再用短事务换分区。页面改成可以勾选多个省 | 页面的多选、缩放适配、瓦片缓存刷新留下了。旁路表没有留下 |
| `d31e3b8`（分支 `cursor/multi-province-tiles-b7ce`） | 也是按省分区，但每个省一张自己的缓冲表。换分区的事务很短，旧分区在事务提交之后再删除。锁等太久会重试 | 这是现在的发布方式 |

合并进主分支的两个提交是 `a869a06` 和 `6b9149b`。冲突不能两套发布逻辑并存，所以收成下面这一套：

- **发布**用分省缓冲表：慢的几何转换和建索引不碰地图正在读的分区；换分区是一次很短的事务；删掉旧分区发生在事务提交之后。
- **地图**用多选：勾选哪些省，瓦片、图层数量、搜索和视野分析就查哪些省。发布成功后瓦片地址会变一次，避免浏览器继续用两分钟缓存里的旧图。

1971 那套公共旁路表在合并时拿掉了。它把「删除旧分区」放在换分区的同一个事务里。旧分区如果有几十万行，删除本身就会把锁持很久，其他省的切片还是会被堵住。分省缓冲表把删除挪到事务外面，就是为了避开这一点。

## 5. 现在的数据放在哪

逻辑上地图只认一张表：`osm_feature`。物理上它是 **LIST 分区表**，分区键是 `region_code`。安徽的行实际躺在 `osm_feature_p_anhui`，浙江在 `osm_feature_p_zhejiang`。查询写 `FROM osm_feature` 时，PostgreSQL 会自己找到对应的分区。

分区表的主键必须包含分区键，所以主键是 `(id, region_code)`，不是单独的 `id`。

和发布有关的表名由 `FeatureTables` 生成，省份代码只允许小写字母，避免表名被拼进 SQL 时带进别的字符：

| 名字 | 例子 | 什么时候存在 |
| --- | --- | --- |
| `osm_feature_stage` | 固定这一张 | 解析时暂存 WKT 文本，没有几何索引。切片不读它 |
| `osm_feature_b_{省}` | `osm_feature_b_zhejiang` | 发布前的缓冲。几何和索引都在这里建好 |
| `osm_feature_p_{省}` | `osm_feature_p_zhejiang` | 已经挂到 `osm_feature` 上的正式分区，切片读的就是它 |
| `osm_feature_o_{省}` | `osm_feature_o_zhejiang` | 换下来的旧分区。事务提交后删除 |

`stage` 是 `UNLOGGED`。数据库崩溃时它可以丢，正式分区仍是上一版完整数据。

如果机器上还是今天之前的普通表（没有分区），入库服务启动时 `OsmFeatureSchema` 会做一次迁移：先把数据复制到新的分区表 `osm_feature_next`，索引也在新表上建好，最后才改名。复制期间切片仍读旧表。改名是迁移里唯一会短暂挡住读写的时刻。

## 6. 跟着一次「下载浙江」走

页面上有两个互相独立的选择：

- **地图省份**：多选，决定画哪些省。存在浏览器 `localStorage` 的 `aomap.mapRegions`。
- **数据入库**：单选，决定这一次下载哪个省。

选中浙江并点下载之后，入库服务只允许同时有一个 `RUNNING` 任务（部分唯一索引 `uq_ingest_job_running`）。任务在单独的线程里跑，阶段依次是下载、解析、入库、索引。

### 6.1 下载和解析不碰正式表

下载只写磁盘上的 PBF。解析由 `OsmImporter` 完成：Osmosis 把文件读成节点和道路，分类器决定这条要素属于哪个图层，几何先变成 WKT 文本，用 PostgreSQL 的 `COPY` 批量写入 `osm_feature_stage`。

这一步不更新 `osm_feature`。所以安徽的瓦片查询和浙江的解析互不影响。

### 6.2 入库：把缓冲变成「还没挂上的分区」

解析结束后，`OsmImporter.importFile` 调用：

1. `startBuild`：丢掉这个省上次没清理掉的缓冲表和旧分区，新建 `osm_feature_b_zhejiang`。
2. `copyIntoBuild`：`ST_GeomFromText` 把 WKT 变成真正的几何，写入缓冲表。
3. `indexBuild`：在缓冲表上建主键、GIST 空间索引、图层索引、名称模糊索引，然后 `ANALYZE`。
4. `publishBuild`：短事务里把缓冲表换成正式分区。

第 1 到第 3 步都在独立的表上进行。地图服务的 SQL 是 `FROM osm_feature`，不会去读 `osm_feature_b_zhejiang`。建 GIST 索引很慢，但慢在旁路上，安徽的瓦片继续用原来的分区。

任何一步失败，`abortBuild` 会删掉这张还没挂上的缓冲表。正式地图保持原样。

### 6.3 换分区：事务里只有几句改名

`PublishSql.swap` 在一个事务里执行，并且设置：

- `lock_timeout = 15s`：如果切片查询正占着这张分区，最多等 15 秒，不等待无限久。
- `statement_timeout = 60s`：这一小段语句本身也不允许拖成几分钟。

已经有旧的浙江分区时，顺序是：

```text
ALTER TABLE osm_feature DETACH PARTITION osm_feature_p_zhejiang;
ALTER TABLE osm_feature_p_zhejiang RENAME TO osm_feature_o_zhejiang;
ALTER TABLE osm_feature_b_zhejiang RENAME TO osm_feature_p_zhejiang;
ALTER TABLE osm_feature ATTACH PARTITION osm_feature_p_zhejiang
    FOR VALUES IN ('zhejiang');
COMMIT;
ANALYZE osm_feature_p_zhejiang;
DROP TABLE osm_feature_o_zhejiang;
```

怎么理解这四句：

- `DETACH` 是把旧分区从逻辑表上摘下来。摘下来之后，查 `osm_feature` 的人暂时看不到旧浙江，也还没看到新浙江。
- 两次 `RENAME` 只是改名字，数据不用搬。
- `ATTACH` 把已经建好索引的缓冲表挂回去，并声明「这张表只装 `zhejiang`」。
- `COMMIT` 之后，新的切片查询看到新浙江。
- `DROP` 在提交之后。删大表可能很慢，但它不再和换分区抢同一把锁。

`publishBuild` 如果碰到锁超时（SQLSTATE `55P03`），会最多重试 4 次，每次间隔稍长一点。重试仍然失败时，任务失败，缓冲表被清掉，地图上的旧分区还在。

事务提交前，正在执行的切片语句看到的仍是换分区之前的行。这就是「正在更新的那个省，在切换完成前仍显示旧数据」。

## 7. 一张瓦片是怎么来的

浏览器不会一次把全省要回来。MapLibre 根据当前视野，对每个图层请求很多小方块，例如：

```text
GET /api/tiles/highway/8/210/101.pbf?regions=anhui,zhejiang&v=3
```

`z` 是缩放级别，`x` 和 `y` 是这一层的列和行。`regions` 是当前勾选的省。`v` 是发布次数，用来绕开缓存，下一节再讲。

`TileService` 先做便宜的检查：图层必须是九个之一，`z` 在 0 到 16，`x` 和 `y` 不能跑出这一层的范围。省份用 `Regions.acceptedCodes` 解析：空参数当成安徽；不认识的代码跳过；一个合法省都没有就返回空瓦片，而不是 JSON 错误。空瓦片对 MapLibre 来说就是「这一块没有要素」。

真正的 SQL 在 `TileMapper.xml`，可以分成四步看：

1. `ST_TileEnvelope(z, x, y)` 算出这块瓦片在 Web 墨卡托（EPSG:3857）里的正方形，再转回经纬度，得到和 `geom` 同一坐标系的包围盒。
2. `geom && 包围盒` 只用空间索引找出和这块相交的要素。`region_code IN (...)` 再限定省份。低缩放级别还会丢掉小路、建筑这类细节，否则一块瓦片里的线太多。
3. 低缩放时 `ST_SimplifyPreserveTopology` 把线简化。然后 `ST_AsMVTGeom` 把经纬度几何变成瓦片内部 0–4096 的坐标。
4. `ST_AsMVT` 把这些行打成一块 MVT。MyBatis 不好直接映射 PostGIS 的 `bytea`，所以 SQL 先 `encode(..., 'base64')`，Java 再解码成字节。

要素属性里有 `name`、`subtype`、`layer`、`region`、`osm_id`。点击地图时，弹窗用这些属性显示名字。`region` 就是省级代码，用来区分同一块瓦片里来自不同省的要素。

图层统计、分类统计、搜索、视野分析走同一套省份名单，SQL 同样是 `region_code IN (...)`。搜索结果会多一列省份中文名，因为多个省里可能有同名地点。

这里有两个很像的解析方法，不要混：

- 切片用 `Regions.acceptedCodes`。遇到不认识的代码就跳过，尽量还是画出认识的那些省。
- 统计、搜索、分析用 `Regions.requireCodes`。任何一个代码不认识就直接报错，避免静默少算一个省。
- `RegionSelection` 是另一套解析，`PublishPlanTest` 锁住了它的行为。当前瓦片和统计的主路径不调用它。

## 8. 页面怎么把多个省画在一起

MapLibre 里，每个图层仍是一个矢量源，例如道路一个源、水体一个源。多省不是「一个省一个源」，而是 **一个源的 URL 里带上所有选中的省**。`MapView` 拼出来的地址是：

```text
/api/tiles/{图层}/{z}/{x}/{y}.pbf?regions=anhui,zhejiang&v=3
```

省份会去重、排序。排序是为了让「先选浙江再选安徽」和「先选安徽再选浙江」落到同一个 URL，浏览器缓存才能复用。

`v` 是 `tileRevision`。某个入库任务从 `RUNNING` 变成成功或失败时，页面把这个数字加一。瓦片响应带有两分钟的公共缓存。如果不改 URL，发布完成后的两分钟里，地图可能还在画旧浙江。数字一变，URL 就变了，MapLibre 会重新要瓦片。

勾选变化时会做三件事：

1. `mapRegions` 写入 `localStorage`，刷新页面还在。
2. 图层数量重新请求 `/api/geo/layers?regions=...`，数字是这些省的合计。
3. 如果新勾上的是一个省，地图飞到这个省的中心。点「缩放」则用这些省的中心估一个矩形，`fitBounds` 把它们一起放进屏幕。

顶栏在任务运行时显示「任务进度 · 地图仍显示 安徽省、浙江省」。这是在说明：下载浙江不会把安徽从地图上拿掉。

对话请求会带上 `regionCodes`，也就是当前勾选的名单。`ChatService` 把这份名单传给地图服务，所以「统计道路」统计的是地图上正在看的那些省，不是永远只统计安徽。

## 9. 用时间线把两件事叠在一起看

假设安徽已发布，用户又勾选了浙江并开始下载浙江。

```text
时间        入库线程在做什么                         地图线程在读什么
下载        拉 PBF 到磁盘                            osm_feature_p_anhui
解析        COPY 进 osm_feature_stage                同上，浙江还没有正式分区
建缓冲      写 osm_feature_b_zhejiang 并建索引       同上，缓冲表不在查询路径上
换分区      短事务 DETACH / RENAME / ATTACH          提交前仍是旧数据；提交后读到新浙江
删旧分区    DROP osm_feature_o_zhejiang              已经在读新分区，删除不再挡住它
```

如果浙江以前发布过，换分区提交前地图上的浙江仍是上一版。安徽在整段时间里都还在。

## 11. 今天没有改变的限制

这些限制今天的提交没有打开，读代码时不要误以为已经支持：

- 同一时刻仍然只有一个入库任务。`osm_feature_stage` 只有一张，两个省不能并行解析。
- 关系（OSM relation）仍然不入库。行政区划只用带标签的 way。
- 省界两侧的同一条路可能在两个省的提取里各出现一次。表上没有按 `(region_code, osm_id)` 去重。
- 对话里的「定位到杭州」会飞到坐标，不会自动把浙江勾进地图省份。
- 瓦片仍是现算的，没有预先生成的全国瓦片文件。省多了以后，低缩放级别的查询会更重。
